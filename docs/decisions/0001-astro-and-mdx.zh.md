# 0001 · 使用 Astro 和 MDX

[English](0001-astro-and-mdx.md) · 中文

- 状态：已采纳
- 日期：2026-10

## 背景

这是一个以阅读为主的个人技术博客。大部分页面是静态文章，但部分文章需要嵌入交互演示，比如可以调整参数的频控滑动窗口演示。

需求是：页面加载快；写文章像写 Markdown 一样简单；需要时能嵌入用 React 写的交互组件。

## 决定

框架用 Astro，文章用 MDX。纯文字文章用普通 Markdown（`.md`），只有带交互组件的文章才用 MDX（`.mdx`）。

## 为什么是 Astro

Astro 是面向内容型网站的元框架，和 Next.js 处在同一层：负责路由、页面怎么渲染、网站怎么构建和部署。底层用 Vite 构建。

它的核心思路是默认不向浏览器发送 JavaScript。构建时把页面渲染成纯 HTML，只有明确标记为可交互的组件才加载 JS。这叫岛屿架构（islands architecture），也叫部分水合（partial hydration）：

```astro
<FreqDemo client:visible />  <!-- 组件滚动到可见区域时才加载它的 JS -->
```

一篇文章通常大部分是静态文字，只有一两个演示。用 Astro，读者只需要下载这几个演示的 JS，其余部分是纯 HTML，加载很快。

组件仍然可以用 React 写，不需要学新的组件语法。

## 为什么是 MDX

MDX 是 Markdown 加 JSX。文章里可以 import 组件，像写 HTML 标签一样使用：

```mdx
import FreqDemo from '../components/FreqDemo.jsx';

在下面的演示里调整时间窗口和次数上限：

<FreqDemo window={60} limit={3} client:visible />
```

## 备选方案

### Next.js

React 团队推荐的元框架，面向完整的 Web 应用，能力最全。

没选的原因：页面默认带 React 运行时，对以静态文章为主的网站来说偏重，起步配置也更多。以后如果要做有账号、有数据库的产品，Next.js 更合适。

### VitePress

配置极少，很适合文档站。

没选的原因：它面向文档设计，在文章里嵌入交互组件不如 MDX 自然。

### Markdoc

Stripe 开源的写作格式。文章里不能写 JavaScript，只能使用事先在配置文件里注册的标签，比如 `{% callout %}`。

它的优点是真实存在的：

- 语法更宽松。MDX 会把正文里的 `<` 和 `{` 当成 JSX 解析，写 `O(n) < O(n²)` 不转义就会编译失败。Markdoc 没有这个问题。
- 内容是数据而不是代码，翻译和多人协作时不容易被改坏。

没选的原因：

- 它的约束是为多人维护的大型文档站设计的。这个博客只有一个作者，而且作者是前端工程师，这些约束带来的好处不大。
- 博客的重点是交互演示。在 Markdoc 里，每个组件都要先注册标签和参数结构。在 Astro 里，Markdoc 标签不能直接使用 `client:visible` 这类指令，交互组件需要额外包一层 Astro 组件。每做一个演示都多一道手续。
- MDX 的生态和学习资料更多。

MDX 的语法问题，用"纯文字文章写 `.md`，只有交互文章写 `.mdx`"来规避。

## 影响

- `.mdx` 文章正文里的 `<` 和 `{` 必须转义，或者放进代码块。
- MDX 不支持 HTML 注释（`<!-- -->`）。
- Astro 更新很快，很多教程已经过时。以已安装版本的官方文档为准。
- 如果以后每篇文章都要翻译成多种语言，并借助批量翻译工具，MDX 文章里的 JSX 在翻译时容易被改坏。到时候需要重新评估这个决定。
